# مقایسه جامع Tuple و Class در C# (کدام را انتخاب کنیم؟)

در توسعه نرم‌افزار با C#، یکی از چالش‌های رایج، انتخاب ساختار مناسب برای گروه‌بندی داده‌هاست. آیا باید یک `Class` بسازیم یا از `Tuple` استفاده کنیم؟ این مقاله به‌صورت جامع و موشکافانه این دو مفهوم را از ۱۹ زاویه مختلف بررسی می‌کند تا در معماری نرم‌افزار خود بهترین تصمیم را بگیرید.

<a id="مقدمه"></a>
## مقدمه
در C# مدرن (از نسخه 7 به بعد)، وقتی از Tuple استفاده می‌کنید، در واقع در حال استفاده از `ValueTuple` هستید. کلاس‌ها (`Class`) ستون فقرات برنامه‌نویسی شی‌ءگرا هستند، در حالی که Tuples ساختارهایی سبک، موقت و برای انتقال دسته‌ای داده‌ها طراحی شده‌اند. انتخاب اشتباه بین این دو می‌تواند منجر به کاهش Performance، مشکلات در Serialization و کاهش خوانایی کد شود.

<a id="مقایسه-ساختاری-و-مفهومی"></a>
## ۱. مقایسه ساختاری و مفهومی (۱۹ معیار)

برای درک عمیق، این ۱۹ معیار را در ۵ دسته‌بندی منطقی بررسی می‌کنیم:

<a id="ماهیت-و-تعریف"></a>
### 🔹 ماهیت و تعریف
1. **تعریف (Definition):**
   * **Class:** یک الگو (Blueprint) برای ساخت اشیاء است که داده‌ها و رفتارها (متدها) را در کنار هم قرار می‌دهد.
   * **Tuple:** یک ساختار داده سبک برای گروه‌بندی موقت تعداد مشخصی از داده‌ها (ممکن است از انواع مختلف باشند) بدون در نظر گرفتن رفتار.
2. **Type Name:**
   * **Class:** دارای یک نام مشخص و منحصربه‌فرد است (مثلاً `User`).
   * **Tuple:** نام نوع آن بر اساس Generic تعریف می‌شود (مثلاً `ValueTuple<int, string>`). *نام‌گذاری المان‌ها (Element Names) فقط در زمان کامپایل توسط Compiler پشتیبانی می‌شود و در Metadata اسمبلی ذخیره نمی‌شود.*
3. **Value Type / Reference Type:**
   * **Class:** یک **Reference Type** است و روی Heap تخصیص می‌یابد.
   * **Tuple:** (در C# مدرن) یک **Value Type** (ساختار `struct`) است و معمولاً روی Stack تخصیص می‌یابد.

<a id="ساختار-داخلی"></a>
### 🔹 ساختار داخلی
4. **Property:**
   * **Class:** پشتیبانی کامل از Propertyها (با `get` و `set` و Access Modifier).
   * **Tuple:** **Property ندارد**. المان‌های Tuple در واقع **Field**های عمومی هستند.
5. **Field:**
   * **Class:** می‌تواند Field داشته باشد.
   * **Tuple:** تمام المان‌های آن (مثل `Item1`, `Item2` یا نام‌های سفارشی) در واقع **Public Field** هستند.
6. **Method:**
   * **Class:** می‌تواند متدها و رفتارهای دلخواه داشته باشد.
   * **Tuple:** **هیچ متد سفارشی نمی‌پذیرد** (فقط متدهای ارث‌بری شده از `Object` مثل `ToString` و `Equals`).
7. **Constructor:**
   * **Class:** دارای Constructorهای سفارشی و پیچیده.
   * **Tuple:** Constructor سفارشی ندارد و فقط با سینتکس `(val1, val2)` یا `new ValueTuple(...)` ساخته می‌شود.

<a id="اصول-شیءگرایی"></a>
### 🔹 اصول شی‌ءگرایی (OOP)
8. **Encapsulation (کپسوله‌سازی):**
   * **Class:** پشتیبانی کامل (می‌توان فیلدها را `private` و دسترسی را محدود کرد).
   * **Tuple:** **هیچ کپسوله‌سازی ندارد** (تمام فیلدها `public` هستند).
9. **Inheritance (وراثت):**
   * **Class:** پشتیبانی کامل از ارث‌بری.
   * **Tuple:** **غیرقابل ارث‌بری** (کلاس `sealed` است).
10. **Interface (پیاده‌سازی رابط):**
    * **Class:** می‌تواند Interfaceها را پیاده‌سازی کند.
    * **Tuple:** **امکان‌پذیر نیست**.

<a id="تغییرپذیری-و-برابری"></a>
### 🔹 تغییرپذیری و برابری
11. **Immutability (تغییرناپذیری):**
    * **Class:** بسته به طراحی (معمولاً Mutable است، مگر اینکه فیلدها `readonly` باشند یا از `record` استفاده کنیم).
    * **Tuple:** **Mutable است**. شما می‌توانید مقدار `Item1` را پس از ساخت تغییر دهید. *(نکته: اگر تغییرناپذیری می‌خواهید، Tuple گزینه مناسبی نیست).*
12. **Mutability (تغییرپذیری):**
    * **Class:** به‌صورت پیش‌فرض Mutable است.
    * **Tuple:** کاملاً Mutable است (تغییر فیلدها مجاز است).
13. **Equality (برابری):**
    * **Class:** مقایسه بر اساس **Reference** (آدرس حافظه) است، مگر اینکه `Equals` و `==` را Override کنید.
    * **Tuple:** مقایسه بر اساس **Value** (مقدار تک‌تک المان‌ها) است.

<a id="معماری-و-نگهداری"></a>
### 🔹 معماری و نگهداری
14. **Maintainability (نگهداری‌پذیری):**
    * **Class:** **بسیار بالا**. نام‌گذاری واضح، تایپ‌سیف و مستندات XML.
    * **Tuple:** **پایین در مقیاس بزرگ**. استفاده از `Item1` و `Item2` کد را غیرخوانا می‌کند. نام‌گذاری المان‌ها کمک‌کننده است اما در Reflection یا LINQ به SQL مشکل‌ساز می‌شود.
15. **Serialization:**
    * **Class:** **عالی**. سازگاری کامل با JSON, XML, Entity Framework.
    * **Tuple:** **بسیار ضعیف**. به دلیل Public بودن فیلدها و نام‌های Generic، در کتابخانه‌های Serialization (مثل System.Text.Json) و ORMها (مثل EF Core) به‌درستی مپ نمی‌شوند.
16. **API (Public Contracts):**
    * **Class:** استاندارد طلایی برای Public APIها و DTOها.
    * **Tuple:** **هرگز در Public API استفاده نشود**. نام المان‌های Tuple در زمان کامپایل از بین می‌رود و در اسمبلی‌های دیگر به صورت `Item1` دیده می‌شود.
17. **Domain Model (مدل دامنه):**
    * **Class:** **ایده‌آل**. برای ساخت Entityها و Value Objectها در DDD.
    * **Tuple:** **ممنوع**. مدل دامنه نیازمند رفتار و اعتبارسنجی است که Tuple فاقد آن است.
18. **Performance (عملکرد):**
    * **Class:** تخصیص روی Heap، ایجاد فشار روی Garbage Collector (GC).
    * **Tuple:** تخصیص روی Stack، **بسیار سریع** و بدون فشار روی GC (مگر اینکه Box شود یا بیش از ۷ المان داشته باشد).
19. **قابلیت توسعه (Extensibility):**
    * **Class:** **بالا**. افزودن متد، Property و ارث‌بری.
    * **Tuple:** **صفر**. ساختار آن ثابت است و نمی‌توان رفتار یا منطق جدیدی به آن اضافه کرد.

<a id="مثالهای-کاربری-در-c"></a>
## ۲. مثال‌های کاربردی در C#

```csharp
// 1. تعریف Class
public class User 
{
    public int Id { get; set; }
    public string Name { get; set; }
    
    public void Activate() => Console.WriteLine("Activated"); // دارای رفتار
}

// 2. تعریف Tuple (بدون نام و با نام)
var tuple1 = (1, "Ali"); // المان‌ها: Item1, Item2
var tuple2 = (Id: 1, Name: "Ali"); // المان‌ها: Id, Name (فقط در زمان کامپایل)

// 3. تفاوت در Mutability
var user = new User { Id = 1, Name = "Ali" };
var myTuple = (Id: 1, Name: "Ali");

// myTuple.Id = 2; // مجاز است! (Tuple Mutable است)

// 4. تفاوت در Equality
var t1 = (1, "Ali");
var t2 = (1, "Ali");
Console.WriteLine(t1 == t2); // True (مقایسه Value)

var u1 = new User { Id = 1, Name = "Ali" };
var u2 = new User { Id = 1, Name = "Ali" };
Console.WriteLine(u1 == u2); // False (مقایسه Reference - مگر اینکه Override شود)
```

<a id="سناریوهای-واقعی-و-انتخاب-درست"></a>
## ۳. سناریوهای واقعی و انتخاب درست

### سناریو ۱: متد `TryParse` سفارشی
می‌خواهید متدی بنویسید که یک رشته را بررسی کند و در صورت موفقیت، یک مقدار و یک پیام خطا برگرداند.
* **انتخاب:** **Tuple**
* **دلیل:** این یک داده موقت و داخلی است. ساخت Class برای این کار Over-engineering است.
```csharp
public (bool IsSuccess, string ErrorMessage) ValidateInput(string input)
{
    if (string.IsNullOrEmpty(input)) return (false, "Input is empty");
    return (true, string.Empty);
}
```

### سناریو ۲: بازگشت دادن داده از یک Public API (مثلاً REST Controller)
می‌خواهید اطلاعات کاربر را به کلاینت (فرانت‌اند) بفرستید.
* **انتخاب:** **Class (یا Record)**
* **دلیل:** نیاز به Serialization به JSON دارید. نام Propertyها باید در JSON حفظ شود. Tuple در این سناریو فاجعه بار است.

### سناریو ۳: پروژه کردن (Projection) در LINQ
می‌خواهید از یک لیست بزرگ، فقط دو فیلد را استخراج کنید.
* **انتخاب:** **Tuple** (یا Anonymous Type)
* **دلیل:** سرعت بالا، عدم نیاز به تعریف کلاس جدید، و موقتی بودن داده.
```csharp
var userNames = users.Select(u => (u.Id, u.Name)).ToList();
```

### سناریو ۴: ساخت Domain Entity (مثلاً `Order` یا `Product`)
* **انتخاب:** **Class**
* **دلیل:** نیاز به Encapsulation، اعتبارسنجی در Constructor، متدهای دامنه‌ای (مثل `CalculateDiscount`) و سازگاری با Entity Framework دارید.

| **بازگشت چند مقدار از متد** | ✅ عالی | ❌ نامناسب | ⚠️ خوب |

<a id="نکات-مهم-و-اشتباهات-رایج"></a>
## ۵. نکات مهم و اشتباهات رایج

🚨 **اشتباهات رایج (Anti-Patterns):**
1. **استفاده از Tuple در Domain Model:** هرگز برای Entityهای دیتابیس یا مدل‌های دامنه از Tuple استفاده نکنید. این کار باعث از بین رفتن Encapsulation و بروز باگ‌های سخت‌دیباگ می‌شود.
2. **استفاده از Tuple در Public API:** اگر متدی در یک Library عمومی دارید که Tuple برمی‌گرداند، مصرف‌کننده Library شما در اسمبلی خودش نام المان‌ها را نمی‌بیند (فقط `Item1` را می‌بیند). همیشه از Class/Record استفاده کنید.
3. **Tuple با بیش از ۷ المان:** در C#، اگر Tuple بیشتر از ۷ المان داشته باشد، Compiler به‌صورت خودکار آن را به صورت **تو‌در‌تو (Nested)** با استفاده از فیلدی به نام `Rest` می‌سازد. این کار هم Performance را به‌شدت کاهش می‌دهد و هم خوانایی را نابود می‌کند.

💡 **نکات طلایی (Best Practices):**
* **قانون طلایی:** اگر داده‌ها **رفتار (Behavior)** دارند یا قرار است **بیش از یک متد/لایه** دست‌به‌دست شوند، حتماً از **Class** (یا **Record**) استفاده کنید.
* اگر داده‌ها فقط **مجموعه‌ای از مقادیر موقت** برای انتقال از یک متد به متد دیگر هستند، **Tuple** بهترین و سریع‌ترین گزینه است.
* از C# 9 به بعد، اگر به دنبال ساختاری هستید که هم مثل Tuple سبک باشد و هم مثل Class نام‌دار و Immutable، از **`record`** استفاده کنید.

<a id="جمع‌بندی"></a>
## ۶. جمع‌بندی
انتخاب بین `Tuple` و `Class` انتخاب بین "سرعت و سبکی" در برابر "ساختار و معماری" است.
* **Tuple** را برای کارهای **داخلی، موقت، محاسباتی و LINQ** نگه دارید.
* **Class** را برای **معماری سیستم، مدل‌های دامنه، DTOها و APIها** استفاده کنید.
* به یاد داشته باشید که در C# مدرن، **`record`** جایگزین بی‌نظیری برای کلاس‌هایی است که صرفاً حامل داده (Data Carrier) هستند و نیاز به تغییرناپذیری دارند.
