## بخش اول: مفاهیم پایه

### ۱. try چیست؟
بلوک `try` مانند یک **اتاق شیشه‌ای محافظ** است. شما کدی را که احتمال می‌دهید در آن خطایی رخ دهد (مثل خواندن فایل، اتصال به دیتابیس یا تقسیم بر صفر) داخل این بلوک قرار می‌دهید تا در صورت بروز مشکل، برنامه کرش (Crash) نکند.

### ۲. catch چیست؟
بلوک `catch` مانند **آتش‌نشان** است. اگر در بلوک `try` آتشی روشن شود (خطایی رخ دهد)، `catch` وارد عمل شده، خطا را مدیریت می‌کند (لاگ می‌گیرد، به کاربر پیام می‌دهد یا مسیر را تغییر می‌دهد) و اجازه می‌دهد برنامه به حیات خود ادامه دهد.

### ۳. finally چیست؟
بلوک `finally` **نظافتچی همیشگی** است. کدی که در این بلوک می‌نویسید، **چه خطا رخ دهد و چه ندهد**، در نهایت اجرا می‌شود. این بلوک برای آزادسازی منابع (مثل بستن فایل‌ها یا اتصال دیتابیس) حیاتی است.

### ۴. قوانین ترکیب try, catch و finally
* شما نمی‌توانید `try` را به تنهایی بنویسید.
* ترکیب‌های مجاز:
  * `try` + `catch` (یک یا چند بلوک)
  * `try` + `finally`
  * `try` + `catch` + `finally`

### ۵. دسترسی catch به شیء Exception
وقتی خطایی رخ می‌دهد، #C یک شیء از کلاس `Exception` (یا کلاس‌های ارث‌بری شده از آن) می‌سازد. شما در `catch` به این شیء دسترسی دارید:
```csharp
try { /* ... */ }
catch (Exception ex) {
    Console.WriteLine(ex.Message); // پیام خطا
}
```

### ۶. مدیریت خطا یا دوباره پرتاب کردن (Rethrow)
* **مدیریت (Handle):** خطا را در همان متد رفع می‌کنید (مثلاً با نشان دادن پیام به کاربر).
* **پرتاب مجدد (Rethrow):** متد فعلی توانایی رفع خطا را ندارد، پس آن را به متد فراخوانی‌کننده (Caller) پاس می‌دهد تا آنجا تصمیم بگیرد.

### ۷. چه زمانی Exception را دوباره throw کنیم؟
زمانی که متد شما فقط یک لایه از منطق است (مثلاً یک متد Repository برای دیتابیس) و نمی‌داند خطا باید چگونه به کاربر نهایی نمایش داده شود. در این حالت خطا را می‌گیرید، لاگ می‌کنید و به لایه بالاتر (مثلاً Service یا Controller) پاس می‌دهید.

### ۸. ترتیب بررسی بلوک‌های catch
#C بلوک‌های `catch` را **از بالا به پایین** بررسی می‌کند. بنابراین، همیشه باید **خطاهای خاص‌تر** را در بالا و **خطاهای عمومی‌تر** را در پایین بنویسید.
```csharp
catch (FileNotFoundException ex) { ... } // خاص
catch (IOException ex) { ... }           // عمومی‌تر
catch (Exception ex) { ... }             // عمومی‌ترین
```

### ۹. استفاده از when در catch (Exception Filters)
از #C 6.0 به بعد، می‌توانید شرط بگذارید که `catch` فقط در صورتی اجرا شود که یک شرط خاص برقرار باشد. این کار از تغییر Stack Trace جلوگیری می‌کند.
```csharp
catch (HttpRequestException ex) when (ex.StatusCode == 404) {
    // فقط اگر خطای 404 بود اجرا شود
}
```

## بخش دوم: مسیر اجرا و Stack Trace

### ۱۰. Control Flow در حالت عادی
در حالت عادی، کد خط به خط از بالا به پایین اجرا می‌شود. متدها همدیگر را صدا می‌زنند و پس از اتمام کار، کنترل به متد قبلی برمی‌گردد.

### ۱۱. Exception Flow چیست؟
وقتی خطایی رخ می‌دهد، جریان عادی اجرای برنامه **شکسته** می‌شود. #C به دنبال متدی می‌گردد که بتواند این خطا را مدیریت کند. این جستجو ممکن است چندین متد را در Call Stack به عقب برگرداند.

### ۱۲ تا ۱۴. مراحل وقوع و ساخت Exception
1. **وقوع خطا:** مثلاً دسترسی به فایل ممنوع می‌شود.
2. **ساخت شیء:** Runtime یک شیء `Exception` در حافظه Heap می‌سازد.
3. **اطلاعات شیء:**
   * **Message:** توضیح متنی خطا.
   * **StackTrace:** مسیر متدهایی که تا نقطه خطا طی شده‌اند.
   * **InnerException:** اگر خطای فعلی ناشی از یک خطای دیگر باشد.
   * **HResult:** یک کد عددی (Hex) برای شناسایی نوع خطا در سطح سیستم‌عامل.

### ۱۵. Capture شدن Stack Trace
**نکته طلایی:** Stack Trace در لحظه‌ای که `throw` می‌کنید (یا Runtime خطا را می‌سازد) ثبت می‌شود، **نه** در لحظه‌ای که آن را `catch` می‌کنید.

### ۱۶. Stack Frame چیست؟
هر بار که یک متد صدا زده می‌شود، یک **Stack Frame** (قاب پشته) روی Call Stack ساخته می‌شود. این فریم شامل متغیرهای محلی، پارامترها و آدرس بازگشت به متد قبلی است.

### ۱۷. Stack Frame Walking
وقتی خطایی رخ می‌دهد، Runtime شروع به **پیمایش پشته (Walking)** می‌کند؛ یعنی از فریم فعلی به سمت فریم‌های قبلی (متدهای فراخوانی‌کننده) حرکت می‌کند تا ببیند آیا کسی این خطا را مدیریت کرده است یا خیر.

### ۱۸ و ۱۹. Stack Unwinding (باز کردن پشته)
اگر در متد فعلی `catch` مناسبی پیدا نشود، Runtime شروع به **Unwinding** می‌کند. یعنی فریم‌های پشته را یکی‌یکی دور می‌ریزد و **تمام بلوک‌های `finally`** را در مسیر خود اجرا می‌کند تا منابع پاکسازی شوند.

### ۲۰ و ۲۱. پیدا کردن Handler مناسب
Runtime در هر متد به دنبال بلوک `catch` می‌گردد. اگر پیدا کرد، اجرای برنامه از همان نقطه ادامه می‌یابد. اگر پیدا نکرد، به متد بالایی می‌رود (همان Unwinding).

### ۲۲ و ۲۳. Exception Handler Table (EHTable) و IL
وقتی کد شما کامپایل می‌شود، به زبان IL تبدیل می‌شود. در IL، برای هر متدی که `try/catch` دارد، یک جدول به نام **EHTable** ساخته می‌شود. این جدول به Runtime می‌گوید: *"اگر بین خط X و Y خطایی از نوع Z رخ داد، برو به خط W (شروع بلوک catch)"*.

### ۲۴. نقش JIT و Runtime
JIT Compiler هنگام تبدیل IL به کد ماشین، EHTable را می‌خواند. وقتی خطایی رخ می‌دهد، این **Runtime** است که با استفاده از این جدول، سریعاً آدرس Handler مناسب را پیدا می‌کند.

### ۲۵. Stack Trace و Lazy Construction
ساخت رشته متنی `StackTrace` بسیار سنگین است. #C این کار را **Lazy** (تنبل‌وار) انجام می‌دهد. یعنی تا زمانی که شما `ex.StackTrace` را نخوانید یا `ex.ToString()` را صدا نزنید، این رشته ساخته نمی‌شود تا در مصرف حافظه و CPU صرفه‌جویی شود.

### ۲۶. رسیدن به Handler مناسب
پس از پیمایش و Unwinding، وقتی Handler پیدا شد، کنترل برنامه به بلوک `catch` منتقل شده و برنامه از حالت بحرانی خارج می‌شود.

## بخش سوم: هزینه و عملکرد (Performance)

### ۲۷. چرا Exception گران است؟
استفاده از Exception برای کنترل جریان برنامه (Control Flow) یک **جنایت_performance** است! هزینه آن فقط مربوط به لحظه `throw` نیست.

### ۲۸ تا ۳۲. تفکیک هزینه‌ها
1. **هزینه ساخت:** تخصیص حافظه در Heap برای شیء Exception.
2. **هزینه Capture:** پیمایش Call Stack برای ساخت Stack Trace (بسیار سنگین).
3. **هزینه Unwinding:** جستجو در EHTable و اجرای بلوک‌های `finally`.
4. **هزینه JIT/Runtime:** وجود بلوک‌های `try/catch` در کد، جلوی برخی بهینه‌سازی‌های JIT (مثل Inlining متدها) را می‌گیرد.

## بخش چهارم: تفاوت throw و throw ex

این یکی از مهم‌ترین مباحث در مصاحبه‌های سطح Senior است.

### ۳۳ و ۳۴. throw; (حفظ Stack Trace)
وقتی می‌نویسید `throw;` (یا فقط `throw`)، شما خطای قبلی را **دقیقاً با همان Stack Trace اصلی** به متد بالایی پاس می‌دهید.
```csharp
try { DoSomething(); }
catch (Exception ex) {
    Log(ex);
    throw; // Stack Trace دست‌نخورده باقی می‌ماند
}
```

### ۳۵ و ۳۶. throw ex; (Reset شدن Stack Trace)
وقتی می‌نویسید `throw ex;`، شما یک **خطای جدید** پرتاب می‌کنید. در نتیجه، Stack Trace از همین نقطه (متد فعلی) شروع می‌شود و **ریشه اصلی خطا گم می‌شود!**

### ۳۷ و ۳۸. مقایسه و نتیجه‌گیری
* **`throw;`** مثل فوروارد کردن یک ایمیل است (تاریخچه حفظ می‌شود). ✅ **همیشه از این استفاده کنید.**
* **`throw ex;`** مثل این است که یک ایمیل جدید بنویسید و بگویید "مشکلی پیش آمد" (تاریخچه پاک می‌شود). ❌ **هرگز استفاده نکنید.**

## بخش پنجم: کاهش هزینه و الگوهای جایگزین

### ۳۹. چرا نباید از Exception برای Control Flow استفاده کرد؟
چون Exception برای **شرایط استثنایی و غیرمنتظره** طراحی شده است. مثلاً چک کردن اینکه "آیا کاربر این فایل را دارد یا نه" یک اتفاق روزمره است، نه استثنایی.

### ۴۰. الگوی Result Object
به جای پرتاب Exception، یک کلاس Result برمی‌گردانیم:
```csharp
public class Result<T> {
    public bool IsSuccess { get; set; }
    public T Value { get; set; }
    public string Error { get; set; }
}
```

### ۴۱ و ۴۲. الگوی Try Pattern (مثل TryParse)
در این الگو، متد یک `bool` برمی‌گرداند و خروجی را در یک پارامتر `out` قرار می‌دهد. این الگو **سریع‌ترین** راه برای مدیریت خطاهای مورد انتظار است.
```csharp
if (int.TryParse(input, out int number)) {
    // موفقیت‌آمیز
} else {
    // خطا بدون هزینه Exception
}
```

### ۴۳ و ۴۴. Guard Clause
به جای اینکه کد را در تو در تو بنویسید و منتظر Exception بمانید، در **ابتدای متد** ورودی‌های نامعتبر را چک کنید و سریعاً خارج شوید (Return کنید یا Exception پرتاب کنید).
```csharp
public void ProcessOrder(Order order) {
    if (order == null) throw new ArgumentNullException(nameof(order)); // Guard Clause
    // منطق اصلی...
}
```

### ۴۵ و ۴۶. استفاده از ExceptionDispatchInfo
اگر در حال نوشتن یک کتابخانه Async هستید و می‌خواهید Exception را از یک Thread به Thread دیگری منتقل کنید بدون اینکه Stack Trace آن خراب شود، از `ExceptionDispatchInfo.Capture(ex).Throw();` استفاده می‌کنید.

## بخش ششم: مدیریت منابع و پاکسازی (Cleanup)

### ۴۷ و ۴۸. اجرای finally با خطا و بدون خطا
بلوک `finally` تضمین می‌کند که کدهای داخل آن اجرا شوند. حتی اگر در بلوک `try` دستور `return` داشته باشید، `finally` **قبل از خروج از متد** اجرا می‌شود.

### ۴۹ تا ۵۱. کاربرد finally و Dispose
وقتی با منابعی کار می‌کنید که مستقیماً با سیستم‌عامل در ارتباط هستند (Unmanaged Resources)، حتماً باید آن‌ها را ببندید. متد `Dispose()` در اینترفیس `IDisposable` دقیقاً برای همین کار است و `finally` بهترین جا برای فراخوانی آن است.

### ۵۲ و ۵۳. دستور using و رابطه آن با finally
دستور `using` در #C فقط یک **Syntactic Sugar** (شکر روی کیک) است. کامپایلر به صورت خودکار `using` را به `try/finally` تبدیل می‌کند.
```csharp
// کدی که شما می‌نویسید:
using (var stream = new FileStream("a.txt", FileMode.Open)) {
    // کار با فایل
}

// کدی که کامپایلر می‌سازد:
var stream = new FileStream("a.txt", FileMode.Open);
try {
    // کار با فایل
}
finally {
    if (stream != null) ((IDisposable)stream).Dispose();
}
```

### ۵۴ و ۵۵. منابعی که نیاز به Cleanup دارند
همیشه برای موارد زیر از `using` یا `try/finally` استفاده کنید:
1. **بستن فایل‌ها** (`FileStream`, `StreamReader`)
2. **بستن Connection دیتابیس** (`SqlConnection`)
3. **آزاد کردن Mutex و Lock** (برای جلوگیری از Deadlock)
4. **بستن Network Sockets** و `HttpClient` (در صورت نیاز به Dispose)
5. **گرافیک‌ها** (`Bitmap`, `Graphics` در GDI+)

## 🍳 تشبیه ساده: رستوران و سرآشپز

فرض کن برنامه ما یک **رستوران** است و متدها (توابع) ما **آشپزها** هستند. هر آشپز یک کار مشخص انجام می‌دهد و اگر مشکلی پیش بیاید، باید به **مدیر رستوران** (یعنی متد بالاتر) خبر بدهد.

---

### مرحله ۱: ورود به `try` (شروع کار عادی)

آشپز وارد آشپزخانه می‌شود و شروع به کار می‌کند:

```csharp
try
{
    int x = 10;
    int y = 0;
    int result = x / y;  // ← اینجا مشکل پیش می‌آید
}
```

تا این لحظه همه چیز عادی است، مثل وقتی که آشپز دارد پیاز خرد می‌کند.

---

### مرحله ۲: وقوع Exception (اتفاق غیرمنتظره)

ناگهان آشپز می‌خواهد ۱۰ را بر ۰ تقسیم کند! این کار در ریاضی و برنامه‌نویسی **غیرممکن** است. 

در این لحظه CLR (یعنی مدیر کل رستوران) یک **برگه گزارش خطا** می‌سازد. این برگه حاوی اطلاعات مهمی است:
- **چه خطایی رخ داد؟** (DivideByZeroException)
- **کجا رخ داد؟** (در خط ۵)
- **مسیر تا اینجا چطور بود؟** (چه متدهایی قبل از این صدا زده شدند)

این برگه در حافظه (Managed Heap) ذخیره می‌شود.

---

### مرحله ۳: توقف اجرای عادی

به محض اینکه خطا رخ داد، **بقیه دستورات داخل `try` دور ریخته می‌شوند**:

```csharp
try
{
    Console.WriteLine("1");     // ✅ اجرا می‌شود
    int x = 10 / 0;             // ❌ خطا اینجا
    Console.WriteLine("2");     // ❌ هرگز اجرا نمی‌شود!
}
```

مثل این است که وقتی آشپز متوجه می‌شود غذا سوخته، دیگر ادامه دستور پخت را دنبال نمی‌کند و کار را متوقف می‌کند.

---

### مرحله ۴: CLR دنبال راه‌حل می‌گردد

حالا CLR (مدیر رستوران) می‌گردد ببیند آیا کسی هست که بتواند این مشکل را حل کند؟

```csharp
catch (DivideByZeroException ex)
{
    // این شخص می‌تواند مشکل تقسیم بر صفر را حل کند
}
catch (Exception ex)
{
    // این شخص هر مشکل دیگری را حل می‌کند
}
```

CLR بلوک‌های `catch` را **از بالا به پایین** چک می‌کند. به محض اینکه یک `catch` مناسب پیدا کرد، بقیه را نادیده می‌گیرد.

---

### مرحله ۵: اجرای `catch` (حل مشکل)

وقتی `catch` مناسب پیدا شد، CLR وارد آن می‌شود و دستوراتش را اجرا می‌کند:

```csharp
catch (Exception ex)
{
    Console.WriteLine(ex.Message);  // پیام خطا را نشان می‌دهد
}
```

اینجا جایی است که برنامه‌نویس تصمیم می‌گیرد با خطا چه کند: پیام به کاربر نشان بدهد، در فایل لاگ بنویسد، یا یک مقدار پیش‌فرض برگرداند.

---

### مرحله ۶: اگر هیچ `catch`ای پیدا نشد؟ (Stack Unwinding)

این مهم‌ترین بخش است! فرض کن سه متد داریم که یکی دیگری را صدا زده:

```
Main() → A() → B() → C()
```

حالا در `C()` یک خطا رخ می‌دهد ولی `C` خودش `catch` ندارد:

```
C() ← خطا اینجا، ولی راه‌حلی ندارد
 ↑
B() ← اینجا هم catch ندارد
 ↑
A() ← اینجا هم catch ندارد
 ↑
Main() ← بالاخره اینجا catch پیدا می‌شود!
```

CLR یکی‌یکی از متدها **خارج می‌شود** و به متد بالاتر می‌رود تا یک `catch` مناسب پیدا کند. به این کار می‌گویند **Stack Unwinding** (یعنی باز کردن پشته مثل یک فنر).

اگر تا `Main` هم هیچ `catch`ای پیدا نشود، برنامه **کرش می‌کند** و بسته می‌شود.

---

## 🎯 نکات تکمیلی مهم (که باید بدانی)

### ۱. تفاوت `throw;` با `throw ex;`

این یکی از مهم‌ترین نکاتی است که خیلی‌ها اشتباه می‌کنند:

```csharp
catch (Exception ex)
{
    // ❌ اشتباه: مسیر اصلی خطا از بین می‌رود
    throw ex;  
    
    // ✅ درست: مسیر اصلی خطا حفظ می‌شود
    throw;     
}
```

**چرا مهم است؟** چون وقتی `throw ex` می‌زنی، انگار خطا همین‌جا در همین متد رخ داده! در حالی که `throw` مسیر واقعی خطا را حفظ می‌کند و دیباگ کردن را راحت می‌کند.

---

### ۲. بلوک `finally` همیشه اجرا می‌شود

اگر منابعی باز کرده‌ای (فایل، اتصال دیتابیس، شبکه)، باید آن‌ها را ببندی. بلوک `finally` **تضمین می‌کند** که دستوراتش اجرا شوند، حتی اگر خطا رخ بدهد:

```csharp
try
{
    var file = File.Open("data.txt");
    // کدی که ممکن است خطا بدهد
}
catch
{
    // مدیریت خطا
}
finally
{
    file.Close();  // ✅ همیشه اجرا می‌شود
}
```

**نکته حرفه‌ای:** به جای نوشتن `try-finally` دستی، از `using` استفاده کن که خودش همین کار را می‌کند:

```csharp
using (var file = File.Open("data.txt"))
{
    // کد
}  // ← اینجا خودکار بسته می‌شود، حتی اگر خطا رخ بدهد
```

---

### ۳. CLR چطور می‌فهمد کدام `catch` برای کدام `try` است؟

شاید فکر کنی CLR در زمان اجرا دارد `if/else` چک می‌کند. **نه!** 

کامپایلر و JIT یک **جدول** (EH Table) می‌سازند که در آن نوشته:
- از آدرس X تا Y یک `try` است
- اگر خطا رخ داد، برو به آدرس Z (که `catch` است)

وقتی خطا رخ می‌دهد، CLR فقط **آدرس فعلی** را در این جدول می‌گردد. اگر خطایی رخ ندهد، این جدول اصلاً خوانده نمی‌شود! به همین دلیل `try-catch` وقتی خطایی رخ ندهد **هیچ هزینه‌ای** ندارد.

---

### ۴. هزینه Exception

ساختن یک Exception، پر کردن Stack Trace، و پیمایش پشته فراخوانی **هزینه پردازشی بالایی** دارد. 

**قانون طلایی:** از Exception فقط برای **شرایط غیرعادی** استفاده کن، نه برای کنترل جریان عادی برنامه.

❌ **اشتباه:**
```csharp
try
{
    int value = int.Parse(userInput);
}
catch
{
    value = 0;  // این کار را با if چک کن!
}
```

✅ **درست:**
```csharp
if (int.TryParse(userInput, out int value))
{
    // موفق
}
else
{
    value = 0;
}
```

## 📋 خلاصه کل فرآیند به زبان ساده

```
شروع try
    ↓
اجرای دستورات
    ↓
آیا خطا رخ داد؟
    │
    ├── خیر → ادامه برنامه به صورت عادی
    │
    └── بله → ساخت برگه خطا (Exception Object)
              ↓
          توقف اجرای بقیه try
              ↓
          جستجو برای catch مناسب
              ↓
          آیا catch پیدا شد؟
              │
              ├── بله → اجرای catch
              │         ↓
              │       اجرای finally (اگر باشد)
              │         ↓
              │       ادامه برنامه
              │
              └── خیر → رفتن به متد بالاتر (Stack Unwinding)
                        ↓
                    آیا در متد بالاتر catch پیدا شد؟
                        │
                        ├── بله → اجرای catch
                        │
                        └── خیر → ادامه به متد بالاتر...
                                  ↓
                              اگر تا Main هم پیدا نشد → کرش برنامه!
```
