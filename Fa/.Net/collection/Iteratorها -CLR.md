## فصل اول: آشنایی با CLR و دنیای حافظه
برای درک رفتار Iteratorها، ابتدا باید بدانیم CLR (Common Language Runtime) چگونه حافظه را می‌بیند.

### استک (Stack) در برابر هیپ (Heap)
*   **Stack (پشته):** مثل یک تکه کاغذ یادداشت روی میز شماست. بسیار سریع، منظم و موقت است. متغیرهای مقدار-محور (Value Types مثل `int`) و اشاره‌گرها اینجا قرار می‌گیرند. به محض تمام شدن متد، پاک می‌شوند.
*   **Heap (حافظه پویا):** مثل یک انبار بزرگ است. اشیاء بزرگ و Reference Types (مثل کلاس‌ها، آرایه‌ها و...) اینجا ذخیره می‌شوند. مدیریت آن بر عهده **GC (Garbage Collector)** است.

> 💡 **نکته کلیدی:** هر وقت کلمه `new` را می‌بینید، یعنی قرار است فضایی در **Heap** رزرو شود.

## فصل دوم: ایجاد Object در Heap
وقتی شما یک شیء می‌سازید، CLR مراحل زیر را طی می‌کند:
1.  **محاسبه اندازه:** CLR بررسی می‌کند شیء چقدر فضا نیاز دارد (به اضافه یک overhead برای SyncBlock و Type Handle).
2.  **تخصیص (Allocation):** اشاره‌گر Heap به اندازه مورد نیاز جلو می‌رود.
3.  **صفر کردن (Zeroing):** تمام فیلدهای شیء به صورت پیش‌فرض `null` یا `0` قرار می‌گیرند.
4.  **اجرای Constructor:** متد سازنده شما اجرا می‌شود.

## فصل سوم: جادوی Iterator و تولید تدریجی داده‌ها
حالا بیایید سراغ `yield return` برویم.

### ارزیابی تنبل‌وار (Lazy Evaluation)
فرض کنید می‌خواهید ۱ میلیون عدد تولید کنید. اگر از یک `List<int>` استفاده کنید، همه آن‌ها یکجا در Heap ساخته می‌شوند و رم را اشغال می‌کنند.
اما با `yield return`، داده‌ها **تدریجی (Gradually)** تولید می‌شوند.

```csharp
public IEnumerable<int> GetNumbers()
{
    Console.WriteLine("شروع متد");
    yield return 1;
    Console.WriteLine("تولید عدد دوم");
    yield return 2;
}
```
⚠️ **سوال مهم: زمان ایجاد Iterator Object کی است؟**
اگر کد زیر را اجرا کنید، **هیچ خروجی‌ای در کنسول نمی‌بینید!**
```csharp
var result = GetNumbers(); // متد اصلا اجرا نمی‌شود!
```
**چرا؟** چون در C#، متدهای Iterator دارای **اجرای تاخیری (Deferred Execution)** هستند. فراخوانی متد، کدهای داخل آن را اجرا نمی‌کند، بلکه فقط یک **Iterator Object** در Heap ایجاد می‌کند و آن را برمی‌گرداند.
کدها تنها زمانی اجرا می‌شوند که شما شروع به خواندن داده‌ها کنید (مثلاً با `foreach` یا `MoveNext()`).

## فصل چهارم: کالبدشکافی کامپایلر و ماشین حالت
اینجا وارد بخش پیشرفته می‌شویم. وقتی شما `yield return` می‌نویسید، کامپایلر C# چه می‌کند؟

### نگهداری State (حافظه وضعیت)
کامپایلر C# متد شما را به یک **کلاس مخفی (Hidden Class)** تبدیل می‌کند که یک **ماشین حالت (State Machine)** است.
*   تمام متغیرهای محلی متد شما، به **فیلدهای این کلاس** تبدیل می‌شوند.
*   یک فیلد به نام `<>1__state` وضعیت فعلی اجرای کد را نگه می‌دارد (مثلاً: الان روی خط ۱۰ هستیم یا خط ۲۰؟).

```csharp
// چیزی که کامپایلر می‌سازد (به زبان ساده شده):
private class HiddenStateMachine : IEnumerator<int>
{
    private int state;
    private int currentValue;
    // متغیرهای محلی متد شما اینجا به فیلد تبدیل می‌شوند!
    
    public bool MoveNext() { /* منطق سوییچ کیس بر اساس state */ }
}
```

### Heap Allocation در Iterator
**یک حقیقت تلخ برای Performance:** هر بار که یک متد `yield return` دار را صدا می‌زنید (و شروع به خواندن آن می‌کنید)، کامپایلر یک **شیء جدید از آن کلاس مخفی در Heap ایجاد می‌کند!**
این یعنی Iteratorها ذاتاً باعث **Heap Allocation** می‌شوند.

## فصل پنجم: چرخه حیات، Dispose و نقش CLR
### Lifetime مربوط به Iterator
عمر Iterator دقیقاً به اندازه حلقه `foreach` یا زمانی است که شما در حال خواندن `IEnumerator` هستید. اما اگر حلقه را زودتر قطع کنیم چه؟

```csharp
foreach (var num in GetNumbers())
{
    if (num == 1) break; // حلقه را شکستیم!
}
```
اگر Iterator شما منابعی را باز کرده باشد (مثلاً خواندن از یک فایل یا دیتابیس)، با `break` زدن، آن منابع باز می‌مانند و نشت حافظه رخ می‌دهد!

### اجرای Dispose و نقش CLR در مدیریت منابع
اینجاست که نبوغ کامپایلر C# مشخص می‌شود. کامپایلر به صورت خودکار کدهای `yield` شما را در یک بلوک `try...finally` می‌پیچد.
وقتی `foreach` تمام می‌شود (یا `break` می‌خورد)، متد `Dispose()` روی Iterator Object صدا زده می‌شود.

**در متد Dispose چه اتفاقی می‌افتد؟**
1.  **state** به `-1` تغییر می‌کند (تا دیگر نتوانید `MoveNext` را صدا بزنید).
2.  تمام فیلدهای کلاس مخفی (که متغیرهای محلی شما بودند) **`null`** می‌شوند!
3.  بلوک `finally` شما (اگر نوشته باشید) اجرا می‌شود.

> 🛡️ **نقش CLR:** با `null` کردن فیلدها در `Dispose`، کامپایلر مطمئن می‌شود که Iterator دیگر به اشیاء بزرگ (مثل آرایه‌ها یا دیتابیس) اشاره نمی‌کند. این کار باعث می‌شود **GC (زباله‌روب CLR)** بتواند در اولین فرصت، آن اشیاء بزرگ را از Heap پاکسازی کند.

## فصل ششم: بهینه‌سازی و جلوگیری از Heap Allocation
اگر در حال نوشتن کتابخانه‌های پرformance هستید و نمی‌خواهید Iterator شما در Heap فضا اشغال کند، چه باید کرد؟

### راه حل مدرن: `ref struct` و `Span<T>`
در نسخه‌های جدیدتر .NET، می‌توانید از `ref struct` برای ساخت Enumeratorهای سفارشی استفاده کنید. چون `ref struct`ها **فقط روی Stack** ساخته می‌شوند و اجازه ندارند به Heap فرار کنند!

```csharp
public ref struct MyCustomEnumerator
{
    // این ساختار هرگز در Heap ساخته نمی‌شود!
    private int _current;
    public int Current => _current;
    public bool MoveNext() { ... }
}
```
*نکته: این تکنیک برای حلقه‌های `foreach` کار می‌کند اما برای LINQ یا پاس دادن به عنوان `IEnumerable<T>` مناسب نیست، زیرا `IEnumerable` نیاز به یک کلاس (Reference Type) دارد.*
