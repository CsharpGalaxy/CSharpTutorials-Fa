## 1. مقدمه: چرا اینترفیسها مهم هستند؟
تصور کنید می‌خواهید تابعی بنویسید که لیستی از کاربران را پردازش کند. اگر ورودی تابع را `List<User>` تعریف کنید، هر کس بخواهد آرایه‌ای (`User[]`) یا مجموعه‌ای از دیتابیس (`DbSet`) به شما بدهد، با خطا مواجه می‌شود! 
استفاده از **Interface** به جای **Concrete Class** باعث می‌شود کد شما **انعطاف‌پذیر (Flexible)** و **تست‌پذیر (Testable)** باشد. اما انتخاب اینترفیس *اشتباه* می‌تواند فاجعه‌های بزرگی در **Performance** برنامه شما ایجاد کند.

## 2. معرفی و بررسی اینترفیسها

### 1. `IEnumerable<T>`: پایه و اساس پیمایش
این اینترفیس فقط **یک** قابلیت دارد: توانایی پیمایش (Iteration) روی عناصر با استفاده از `foreach`.
* **ویژگی بارز:** پشتیبانی از **Lazy Evaluation** (ارزیابی تنبلانه). یعنی تا زمانی که روی آن حلقه نزنید، داده‌ای در حافظه تولید یا پردازش نمی‌شود.
* **نقاط ضعف:** نمی‌توانید تعداد عناصر (`Count`) را بدون پیمایش کامل بفهمید. دسترسی به ایندکس (`list[5]`) غیرممکن است.
* **کاربرد:** وقتی فقط می‌خواهید داده‌ها را یک‌بار از اول تا آخر بخوانید (مثل Stream ها یا LINQ Queries).

```csharp
// فقط قابلیت پیمایش دارد
public void ProcessUsers(IEnumerable<User> users)
{
    foreach (var user in users)
    {
        Console.WriteLine(user.Name);
    }
}
```

### 2. `IReadOnlyCollection<T>`: مجموعه فقط خواندنی
این اینترفیس از `IEnumerable<T>` ارث‌بری می‌کند و **یک** ویژگی مهم به آن اضافه می‌کند: `Count`.
* **ویژگی بارز:** تضمین می‌کند که مجموعه قابل تغییر نیست (Add/Remove ندارد) و تعداد عناصر را در **زمان O(1)** (بدون نیاز به پیمایش) برمی‌گرداند.
* **کاربرد:** بهترین گزینه برای بازگرداندن (Return) یک مجموعه از یک متد، زمانی که نمی‌خواهید caller بتواند آن را تغییر دهد اما به تعداد آن نیاز دارد.

```csharp
public IReadOnlyCollection<User> GetActiveUsers()
{
    // ...
}
```

### 3. `ICollection<T>`: مجموعه قابل تغییر
این اینترفیس از `IEnumerable<T>` ارث‌بری می‌کند و قابلیت‌های `Count`، `Add`، `Remove`، `Clear` و `Contains` را فراهم می‌کند.
* **ویژگی بارز:** یک مجموعه کاملاً قابل تغییر (Mutable) است.
* **نقاط ضعف:** هنوز دسترسی به ایندکس (مثلاً `collection[2]`) را پشتیبانی نمی‌کند.
* **کاربرد:** وقتی نیاز دارید داده‌ها را اضافه یا حذف کنید، اما ترتیب یا دسترسی تصادفی (Random Access) برایتان مهم نیست.

### 4. `IList<T>`: لیست با دسترسی تصادفی
این اینترفیس از `ICollection<T>` ارث‌بری می‌کند و قابلیت **Indexer** (`this[int index]`)، `IndexOf`، `Insert` و `RemoveAt` را اضافه می‌کند.
* **ویژگی بارز:** دسترسی به هر عنصر در **زمان O(1)** (بدون پیمایش از ابتدا).
* **کاربرد:** وقتی نیاز دارید به عناصر خاصی بر اساس شماره ایندکس دسترسی پیدا کنید یا ترتیب عناصر برایتان اهمیت دارد.

## 3. جدول مقایسه قابلیت‌ها

| اینترفیس | ارث‌بری از | قابلیت تغییر (Add/Remove) | دسترسی به Count | دسترسی به Index (اینفکس) | پیمایش (foreach) |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **`IEnumerable<T>`** | - | ❌ | ❌ (نیاز به پیمایش) | ❌ | ✅ |
| **`IReadOnlyCollection<T>`** | `IEnumerable` | ❌ | ✅ (سریع - O(1)) | ❌ | ✅ |
| **`ICollection<T>`** | `IEnumerable` | ✅ | ✅ (سریع - O(1)) | ❌ | ✅ |
| **`IList<T>`** | `ICollection` | ✅ | ✅ (سریع - O(1)) | ✅ (سریع - O(1)) | ✅ |

## 4. بررسی Performance: Index Access در برابر Enumeration

یکی از مهم‌ترین مباحث در Performance، درک تفاوت بین **دسترسی به ایندکس** و **Enumeration (پیمایش)** است.

### سناریوی دسترسی به عنصر دهم:
فرض کنید می‌خواهید عنصر دهم یک مجموعه را بگیرید:
* **در `IList<T>` (مثل Array یا List):** موتور سی‌شارپ مستقیماً به آدرس حافظه `BaseAddress + (10 * Size)` می‌رود. **(زمان O(1) - فوق‌العاده سریع)**
* **در `IEnumerable<T>` (مثل یک LINQ Query یا LinkedList):** موتور باید از عنصر اول شروع کند، یکی‌یکی جلو برود تا به عنصر دهم برسد. **(زمان O(N) - کند)**

⚠️ **هشدار Performance:** هرگز روی یک `IEnumerable` از حلقه `for` و ایندکس استفاده نکنید!
```csharp
// ❌ کارایی بسیار پایین (Anti-Pattern)
for (int i = 0; i < 10; i++)
{
    var item = myEnumerable.ElementAt(i); // هر بار از اول شروع به پیمایش می‌کند!
}

// ✅ راه حل صحیح
foreach(var item in myEnumerable) { ... }
// یا اگر حتما ایندکس می‌خواهید:
var myList = myEnumerable.ToList(); 
```

### بهینه‌سازی هوشمند LINQ در Count:
اگر روی یک `IEnumerable` متد `.Count()` را از LINQ صدا بزنید، آیا از اول می‌شمارد؟
**خیر!** تیم سی‌شارپ هوشمندانه‌ای نوشته‌اند. اگر `IEnumerable` شما در باطن یک `ICollection` باشد، LINQ متوجه شده و مستقیماً از `Count` استفاده می‌کند (O(1)). اما اگر باطن آن واقعاً یک `IEnumerable` (مثل یک Yield Return) باشد، مجبور است کل آن را پیمایش کند (O(N)).

## 5. اشتباهات رایج و تله‌های Performance

### 🚨 تله اول: Multiple Enumeration (پیمایش چندباره)
این شایع‌ترین باگ در بین برنامه‌نویسان است.
```csharp
public void DoSomething(IEnumerable<User> users)
{
    // ❌ اشتباه: اگر users یک LINQ Query باشد، اینجا یک بار از دیتابیس خوانده می‌شود
    if (!users.Any()) return; 

    // ❌ فاجعه: اینجا دوباره از اول پیمایش می‌شود و یک کوئری دیگر به دیتابیس می‌زند!
    foreach (var user in users) 
    {
        // ...
    }
}
```
**✅ راه حل:** یا ورودی را به `ICollection` تغییر دهید، یا در ابتدای متد با `ToList()` آن را متریالایز (Materialize) کنید.

### 🚨 تله دوم: بازگرداندن Concrete Types
```csharp
// ❌ بد: کلاس‌های بیرونی به List وابسته می‌شوند
public List<User> GetUsers() => new List<User>(); 

// ✅ عالی: وابستگی را از بین می‌برد و امنیت را بالا می‌برد
public IReadOnlyList<User> GetUsers() => _users.AsReadOnly(); 
```

## 6. قانون طلایی: چگونه اینترفیس مناسب را انتخاب کنیم؟

برای انتخاب اینترفیس، از این درخت تصمیم‌گیری استفاده کنید:

1. **آیا فقط می‌خواهید داده‌ها را بخوانید و تغییری ندهید؟**
   * آیا به `Count` نیاز دارید؟ 👈 **`IReadOnlyCollection<T>`**
   * آیا به `Index` نیاز دارید؟ 👈 **`IReadOnlyList<T>`**
   * آیا فقط پیمایش کافیست؟ 👈 **`IEnumerable<T>`**

2. **آیا نیاز دارید داده‌ها را تغییر دهید (Add/Remove)؟**
   * آیا به `Index` و ترتیب نیاز دارید؟ 👈 **`IList<T>`**
   * آیا فقط اضافه/حذف کردن مهم است؟ 👈 **`ICollection<T>`**

💡 **یک قانون نانوشته در سی‌شارپ:**
> *"ورودی‌های متدها را تا حد امکان **عام‌ترین** اینترفیس (مثل `IEnumerable`) در نظر بگیرید، اما خروجی متدها را **محدودترین** اینترفیس ممکن (مثل `IReadOnlyCollection`) بازگردانید."*
